# 安全模型

这个项目**故意**建立了一条可以从外部触发本机代码执行的通道。
本文档说明它的信任边界、攻击面，以及你该怎样控制风险。

如果你只是想要一个"能收发邮件的 Agent"，**不要启用轮询** —— 用 `agently-mail` skill
在交互式会话里收发就够了。轮询解决的是"人不在电脑前"的场景，代价就是下面这些风险。

---

## 信任边界

```
┌─────────────────────────────────────────────────────────┐
│  完全不可信                                             │
│                                                         │
│   互联网上的任何人 ──── SMTP ────▶ Agent Mail 收件箱     │
│                                        │                │
│                         ┌──────────────┘                │
│                         │  ← 唯一的身份判据：From 地址    │
│                         ▼                               │
│   ┌───────────────────────────────────────────────┐     │
│   │  轮询程序  trustedSenders 白名单               │     │
│   └───────────────────────────────────────────────┘     │
│                         │                               │
│                         ▼                               │
│   ┌───────────────────────────────────────────────┐     │
│   │  headless Agent   ← 提示层约束，非硬沙箱       │     │
│   │  shell / 文件 / 网络工具                       │     │
│   └───────────────────────────────────────────────┘     │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**边界上只有一个判据：邮件的 `From` 地址。**

而 `agently-cli` 目前**不返回 SPF / DKIM / DMARC 验证结果**，所以程序无法区分
"真的来自该地址"和"声称来自该地址"。这不是实现偷懒，是上游 CLI 的能力限制。

---

## 威胁分析

### T1：伪造发件人 → 远程执行 🔴 高

攻击者知道（或猜到）你的 `trustedSenders` 里某个地址，伪造 `From` 发一封邮件，
正文写任意指令。轮询程序会照单全收，唤醒 Agent 执行。

**影响**：以你的身份发信、读取你全部邮件、在 `workspace-write` 沙箱内操作文件与执行命令。

**缓解**：
- `trustedSenders` **只填一个不公开的地址**，不要用容易猜的常见邮箱
- **不要把真实地址提交进任何公开仓库**（本仓库的示例全部是占位符，就是这个原因）
- 缩小权限：见下面"加固建议"

### T2：邮件环路 → 配额耗尽 / 无限执行 🟠 中

回执本身是出站邮件。若它回到本收件箱且发件人在白名单里，就会被当成新指令，
再发一次回执 —— 实测会逐层嵌套（`[Agent Mail] 已执行: [Agent Mail] 已执行: ...`），
直到把每日发信配额烧光。

**缓解**：三道环路防护（自己发的 / 回执前缀 / 封套标记），任一命中即拒绝执行。
`selfAddresses` 留空时会自动从 `agently-cli +me` 识别，避免手写配置漏填。

### T3：提示注入 → 越权动作 🟠 中

邮件正文会被拼进给 Agent 的提示里。正文可以写"忽略你之前的约束"之类的内容，
尝试让 Agent 突破 SCOPE / FORBIDDEN。

**缓解**：封套把授权与禁止写成结构化段落并要求严格遵守；删除类操作在授权层就禁止了。
但**这是提示层约束，不是内核级隔离** —— 一个足够精巧的注入仍可能部分绕过。

### T4：误配置 → 白名单形同虚设 🟡 低

把 Agent Mail 自己的地址填进 `trustedSenders`，或把 `selfAddresses` 留空且自动识别失败，
都可能让程序处理不该处理的邮件。

**缓解**：`trustedSenders` 或 `selfAddresses` 为空时**拒绝启动**（失败安全），
而不是退化成"谁都能触发"。

### T5：本地提权 🟡 低

轮询程序以你的用户身份运行。任何能写 `~/.agently-mail-watch/settings.json`
或替换 `poller.ps1` 的本地进程，都能控制这条通道。

**缓解**：这属于常规本地安全范畴，与其它用户级自动化程序同级。

## 加固建议

按收益从高到低：

1. **白名单只放一个非公开地址。** 最有效的一条。地址越不透明，T1 越难实施。
2. **用独立邮箱做指令源。** 别用你日常对外通信的主邮箱 —— 它太容易被知道。
3. **别把轮询开在存有敏感数据的机器上。** 它是远程执行入口，请按这个前提选机器。
4. **缩小 Agent 权限。** 把 `poller.ps1` 里唤醒 Agent 的那一步换成沙箱更严的 profile，
   或给 Agent 单独的文件系统根目录。`Invoke-MailAgent` 是唯一的耦合点。
5. **定期看日志。** `~/.agently-mail-watch/logs/` 和 `inbox/` 保留了每一封触发邮件
   的完整封套，是可审计的。
6. **不用时真的停掉。** `watch.cmd disable` 会同时移除开机自启并落下 `DISABLED` 标记，
   不是"这次不跑"而是"以后都不跑，直到重新 enable"。

## 已知不做的防护

诚实列出本项目的**非目标**，避免给你错误的安全感：

| 不做的 | 原因 |
|---|---|
| 发件人签名 / 密钥验证 | 依赖上游 CLI 暴露认证结果，目前没有 |
| 硬沙箱隔离 | 依赖 Agent 运行时的沙箱能力，本项目只传提示 |
| 指令内容过滤 / 语义审查 | 不可靠，且会误伤正常指令 |
| 重放保护 | 邮件本身没有防重放语义；只做 `message_id` 去重 |
| 传输加密之外的保护 | 走 SMTP/TLS，与普通邮件同级 |
